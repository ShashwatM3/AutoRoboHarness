# Open-Source Workspace Simulations With Robots Doing Real Tasks

For a **6-hour-15-minute hackathon build on an Apple Silicon Mac**, there is no single open-source project that simultaneously gives you: browser-native startup, convincing warehouse/retail visuals, a mobile manipulator, shelf picking/restocking, 4–12 robots, robot-camera tiles, deterministic headless evaluation, and a permissive asset license. The closest complete simulator is **Webots**; the strongest manipulation/task environment is **RoboCasa**; and the lowest-risk way to get the exact browser experience you described is a **small Three.js stack built from existing open-source dependencies**, using a real robot description and scripted/kinematic task execution rather than attempting to build a full robotics physics stack during the event. Webots already ships a TIAGo mobile-manipulator model with RGB/depth sensing and supports fast non-rendering execution; RoboCasa has hundreds of manipulation tasks and realistic scenes but currently asserts a single robot in its kitchen environment; and `mujoco_wasm` plus `urdf-loaders` gives a genuinely browser-native JavaScript route but leaves the workspace/task glue to you. fileciteturn33file3L61-L68 fileciteturn33file5L107-L114 fileciteturn45file0L2-L16 fileciteturn35file0L2-L2 fileciteturn48file2L23-L35 fileciteturn44file0L2-L2

## Top recommendations

**Webots + TIAGo is the safest whole-simulator choice.** It already gives you the thing that is surprisingly hard to assemble during a hackathon: a recognizable wheeled mobile manipulator, articulated arm, gripper, sensor cameras, real robot physics, a polished overhead 3D renderer, multiple robots in one world, macOS binaries, and a documented fast/no-rendering mode. The TIAGo configuration includes RGB and depth sensing, and Webots also has a special Supervisor-controller concept suitable for observing/manipulating the simulation globally—the natural place to implement your “supervisor brain,” scoring and adversarial scene mutations. fileciteturn31file0L2-L2 fileciteturn33file3L61-L68 fileciteturn33file5L107-L114 fileciteturn45file0L2-L16

What the team would still build is a small warehouse world, a discrete action adapter on top of each robot (`move_to`, `pick`, `place`, `wait`, `reroute`, `charge`), the task/event logger, the supervisor-agent bridge, and the camera-tile UI. Do **not** attempt generic motion planning for every shelf pose during the hack. Predefine perhaps three shelf approach poses and three arm configurations and interpolate between them. For the adversarial moment, let a Supervisor spawn or move a box/human obstacle into a known aisle and force the planner to re-evaluate. **Biggest risk:** the polished simulation runs natively rather than as a normal React/npm application; Webots Cloud exists, but making the entire live experience browser-hosted adds integration work that does not help your three-minute demo. fileciteturn31file0L2-L2

**RoboCasa is the strongest choice if the judges need to see convincing manipulation above everything else.** The current RoboCasa365 release is unusually well aligned with your self-improvement story: 365 tasks, thousands of realistic scenes/objects, demonstrations, seeded environment creation, and—especially relevant to your supervisor concept—per-frame task annotations containing an atomic skill and stage such as pick/place/navigate. It already gives you evidence that looks like a robot doing an actual job rather than an icon traversing a warehouse graph. fileciteturn35file0L2-L2

The team would mainly build a thin task wrapper, failure/event extraction, knowledge-graph updates, adversarial perturbations, and the demo page showing agent-camera observations alongside the supervisor reasoning. A kitchen cabinet can plausibly stand in for retail replenishment: “pick product from counter/cart, navigate/reach, place product into storage.” However, the current kitchen implementation explicitly enforces one robot, despite having rich camera views including an eye-in-hand camera. For the demo, the pragmatic interpretation of “fleet” would therefore be one physically simulated robot plus several logical fleet members or sequential robot episodes sharing the learned knowledge graph. fileciteturn48file2L23-L35 fileciteturn49file0L1-L16 **Biggest risk:** you discover 45 minutes into the hack that the 10-GB asset/setup path or current Mac/MuJoCo environment needs troubleshooting, and the explicit single-robot assertion prevents the visual fleet shot you wanted. fileciteturn35file0L2-L2

**For this particular hackathon, the highest-control option is a browser-native custom scene assembled entirely from open-source dependencies.** This is not candidate #3 in raw simulator completeness; it is the strategy I would seriously consider choosing given the **6:15 hard timebox**. Use Three.js, `urdf-loaders`, a permissively licensed TIAGo description, low-poly CC0 warehouse assets, and either purely scripted kinematics or `mujoco_wasm` only where real physics adds visible value. `urdf-loaders` is Apache-2.0, actively maintained in October 2026, runs through npm, renders URDFs directly in Three.js, and exposes simple joint commands such as `robot.setJointValue(jointName, jointAngle)`. `mujoco_wasm` is MIT, currently maintained, installs with npm and exposes real MuJoCo stepping directly to JavaScript. fileciteturn50file0L2-L2 fileciteturn51file0L2-L2 fileciteturn20file0L1-L2 fileciteturn44file0L2-L2

The important hackathon decision is to **fake only the low-value physics, not the task semantics**. A robot can visibly drive to a rack, raise its torso, articulate its arm, close its gripper, attach the package mesh to the gripper, reverse the sequence at the destination and emit a real structured event. Collision, lateness, blocked-path, drop and near-miss scoring can still be completely real and deterministic in your task engine. The judges see a realistic robot performing recognizable work, while your team spends its scarce time on the self-improving brain. **Biggest risk:** because this is a toolkit rather than an existing integrated simulator, the team owns all the glue and must resist scope creep—especially physically accurate grasping and inverse kinematics.

The browser implementation does **not** need general-purpose continuous robot control. Model each job as a small deterministic state machine:

`IDLE → MOVE_TO_PICK → ALIGN → REACH → GRASP → RETRACT → MOVE_TO_DROP → REACH → RELEASE → DONE`

`MOVE_TO_PICK` moves the root transform along warehouse waypoints. `REACH` interpolates a short table of known TIAGo joint targets using `setJointValue`. `GRASP` reparents the package mesh under the gripper while recording a logical `heldBy` relationship; `RELEASE` restores it to the world scene. That technique is deliberately kinematic, but the resulting **task outcome and failure telemetry can remain genuine**: completion time, blocked duration, replans, near misses, collisions, unsuccessful grasp, drop, wrong shelf, late task and battery cost can all come from the deterministic task engine.

Robot-camera tiles are also simple in this architecture: attach a `PerspectiveCamera` to an appropriate robot link or a fixed transform on each robot, keep one overhead camera, and render the selected robot cameras into separate render targets/components. For a three-minute presentation, four robot tiles are probably more legible than twelve even if the logical fleet contains twelve.

The adversarial agent should mutate a **small finite set of visually obvious parameters**, not generate arbitrary physics: block aisle B with a pallet, spawn a moving human proxy across route C, make shelf approach A unavailable, delay an elevator/door, place a carton at a different shelf height, or mark a charger occupied. The supervisor can then output something interpretable such as:

> `failure: BLOCKED_PATH → evidence: robot-2 camera + occupancy state → graph update: avoid aisle-B while obstacle-17 present → rerun: success`

That makes the “self-improving brain” visibly causal instead of merely showing a second successful animation.

A realistic allocation of the **exact 6h15m** build window would be:

| Build block | Time |
|---|---:|
| App scaffold + warehouse assets + overhead camera | 45 min |
| Load TIAGo; identify useful joints; get one robot moving/reaching | 60 min |
| Discrete pick/place/transport state machine | 90 min |
| Duplicate robots + waypoint routing / task dispatch | 60 min |
| Robot-camera tiles + supervisor/dashboard UI | 45 min |
| Failure injection + metrics + shared-knowledge update | 45 min |
| Demo choreography and visual polish | 30 min |
| **Total** | **6h15m** |

The strict scope rule I would impose is: **if one robot can drive, pick and place by the 1h45m mark, duplicate it; if not, abandon physical grasp simulation entirely and implement the attach/detach kinematic approach.** Physics accuracy is not the differentiator in your pitch—the loop of *attempt → measurable failure → human comparison/supervisor diagnosis → shared knowledge update → successful rerun* is.

One robot-model caveat matters here. **Hello Robot Stretch is technically attractive but its official `stretch_description` material is not as license-clean for your stated preference.** The current Stretch ROS 2 tree contains URDF/Xacro and meshes, but the description license is **CC BY-NC-SA 4.0**, i.e. non-commercial and share-alike. **Final decision:** for the safest single dependency, use **Webots + TIAGo**. For the strongest one-robot manipulation footage, use **RoboCasa**. For the architecture most likely to look exactly like your mock-up—warehouse overhead view, 4–8 visible robots, a grid of onboard cameras, fast adversarial reruns, and everything inside the browser—use **Three.js + `urdf-loaders` + TIAGo + Kenney CC0 assets**, implement deterministic discrete task logic yourself during the hack, and treat MuJoCo WASM as an optional upgrade rather than a dependency you must successfully integrate. The last route sacrifices contact-physics purity, but it maximizes the amount of the three-minute demo devoted to the genuinely novel part of the project: **robots fail, the supervisor understands why, the shared knowledge changes, and the fleet demonstrably performs better on the rerun.**
